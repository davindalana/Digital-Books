## 1. Executive Summary

This audit re-checked the current source tree, the Phase 3.6 release-candidate suite, the Phase 3.6 report, the real-PDF corpus, the processed-book artifacts in the local library, and the macOS build.

Key results:

- **Automated suite**: `flutter test --reporter expanded` → **500 passed, 0 failed**, exit code `0`, 55 s. The failure reported before this audit was **not reproduced**.
- **Static analysis**: `flutter analyze` → **No issues found**.
- **Formatting**: `dart format --output=none --set-exit-if-changed lib test` initially **failed on 89 files**. It now passes after a formatting-only remediation.
- **macOS build**: `flutter build macos --debug` succeeded and the application process launched. GUI interaction could not be validated because screen capture was denied and no reliable native-driving harness is available.
- **Phase 3.6 report**: several claims are **incorrect or only partially verified**, especially the book count, manual-UX framing, pagination geometry, RSS numbers, visual-evidence captions, and two implementation descriptions.
- **Core product**: no reproducible data-corruption, crash, or blank-Book-Mode defect was found in automated testing. Real-book quality remains uneven, with documented limitations for tables, complex mathematics, stale processed documents, scanned books, and some heading reconstruction.

The release recommendation is **CONDITIONAL PASS**, not PASS: automated evidence is substantially stronger than the previous report claimed to be accurate, but native/manual acceptance and several real-book quality issues remain unverified or unresolved.

### 4.2 Previously reported failure

The audit did not reproduce a current failure. Historical evidence from the pre-audit log shows:

- `phase_3_1_real_acceptance_audit_test.dart` failed with **526.4 ms/page** against a `<= 500 ms/page` wall-clock assertion.
- The same test reported an engine-only average of roughly **316 ms/page**.

Root cause: the assertion measured wall-clock time under `flutter test`’s parallel test-file execution. PDF parsing and CPU contention from other isolates can push wall time over 500 ms without an OCR-engine regression.

### 4.3 Test remediation

`test/phase_3_1_real_acceptance_audit_test.dart` now:

- asserts the **OCR engine throughput** against the product budget (`<= 500 ms/page`);
- keeps an end-to-end wall-clock guard (`<= 1000 ms/page`) for gross regressions;
- reports both values in the log.

Isolated rerun after the change: **3/3 passed**, wall **337–388 ms/page**, engine **247–270 ms/page**. The full suite then passed **500/500** with the change present.

This is a measurement correction, not a relaxation of the OCR engine budget.

### 4.4 Test-suite limitations

- Real-book tests use hard-coded local paths under `~/Downloads` and `~/Documents/DigitalBooks`; when absent they `return` early and are counted as passed rather than explicitly skipped.
- Performance numbers are single-run `Stopwatch` samples, not statistically aggregated cold/warm benchmarks.
- Several “UX” tests are service/database/widget tests rather than native application interactions.

### 7.3 Methodology assessment

- Extraction/reconstruction timings vary by roughly 10–40% between isolated and concurrent runs.
- The RSS probe is **not a peak-RSS or leak test**: it samples `ProcessInfo.currentRss` at two points, uses a process-wide value, and does not force GC or track allocations.
- Pagination results are deterministic in page count for a fixed viewport, but latency varies with cache state and machine load.
- The reported 532 ms at 1200×800 is not reproducible; the correct independent measurement at that geometry is about 435 ms for 1,059 pages.

No performance regression was introduced by the audit. No optimization is justified without a reproducible bottleneck.

## 8. Confirmed Defects, Root Causes, and Fixes

### 8.1 Flaky OCR acceptance test

**Symptom**: full-suite failure at `526.4 ms/page` against a 500 ms/page wall-clock bound.

**Root cause**: the test measured wall-clock time while `flutter test` ran test files concurrently; PDF parsing and CPU contention were included in a criterion intended to represent OCR throughput.

**Fix** (`f6d3e5b`): assert the OCR engine metric (`averagePageDurationMs <= 500`) and guard end-to-end wall clock at `<= 1000 ms/page`. Both values are printed for diagnostics.

**Verification**: isolated Phase 3.1 test 3/3 passed with engine 247–270 ms/page; full suite 500/500 passed.

### 8.2 Repository formatting failure

**Symptom**: `dart format --output=none --set-exit-if-changed lib test` exited 1 and reported **89 changed files**.

**Root cause**: the source tree had accumulated formatter drift. Formatting also exposed five `curly_braces_in_flow_control_structures` lints where the formatter broke single-line `if` statements.

**Fix** (`4d3964f`): apply `dart format lib test`; add braces in:
- `lib/features/processing/services/ocr_correction_pass.dart`
- `lib/features/processing/services/scanned_image_enhancer.dart`
- `lib/features/reader/presentation/widgets/original_pdf_reader.dart` (two sites)
- `test/phase_3_0_1_image_enhancement_test.dart`

**Verification**: `flutter analyze` → No issues found; `dart format --output=none --set-exit-if-changed lib test` → exit 0; full suite 500/500 passed.

### 8.3 Report/evidence inaccuracies

**Symptom**: release report overstates manual validation, book coverage, benchmark geometry, memory behavior, and some implementation details.

**Fix** (`Phase 3.7 report`): correct the claims, mark them VERIFIED / PARTIALLY VERIFIED / INCORRECT, and preserve the original report as a historical artifact with an auditor note. No source behavior was changed to make a claim true.

### 8.4 No product-code data-integrity defect found

The audit did not reproduce a crash, import corruption, blank Book Mode, or reading-position loss. Atomic import tests, fallback loader tests, and full-suite navigation tests pass. This is evidence of improvement, not proof that all real-world failure modes are eliminated.

## 9. Remaining Limitations and Risks

1. **No native manual acceptance**: keyboard, pointer, file picker, and visual behavior were not driven by a human or native automation harness.
2. **Stale processed documents**: the *Let Them Theory* library JSON is structurally obsolete (1 chapter, no headings). There is no automatic reprocessing or migration after pipeline improvements.
3. **Heading anomalies in real OCR books**: *Laut Bercerita* has duplicated/misplaced chapter titles. Heading detection is not universally reliable.
4. **Scanned-book dependency on OCR**: Book Mode is not trustworthy until OCR completes and is quality-checked.
5. **Tables and complex mathematics**: Book Mode intentionally linearises tables and cannot reconstruct 2D formulas. Original PDF remains authoritative.
6. **Real-book tests are machine-specific**: hard-coded user paths and silent early returns weaken reproducibility.
7. **RSS methodology**: current measurements cannot support leak-freedom or peak-memory claims.
8. **Formatter remediation**: the 89-file formatting commit is mechanical but large; review should use `git diff --ignore-all-space` only as a guide, because line wrapping changes are not whitespace-only under the current formatter.
9. **macOS build warnings**: linker warnings about a missing Metal toolchain search path were observed; the build still succeeded.

## 10. Release Recommendation

**Verdict: CONDITIONAL PASS**

Rationale supporting release readiness:

- 500 automated tests pass with zero failures.
- `flutter analyze` is clean.
- Formatting validation passes.
- The macOS debug build succeeds and the app launches.
- The high-priority P0/P1 fixes from earlier phases (atomic imports, scanned-state derivation, Book Mode load failure fallback, import-error visibility, content preservation) remain present and covered by regression tests.
- No critical data-loss or crash defect was reproduced.

Conditions attached to the verdict:

1. The Phase 3.6 report must be treated as superseded; its manual-UX, four-book, 1200×800 pagination, RSS, and visual-evidence claims are not accurate.
2. Native manual acceptance of import, reading, typography, themes, annotations, and restart persistence is still outstanding.
3. *Laut Bercerita* heading anomalies and stale processed documents must be treated as known quality issues.
4. Tables, complex mathematics, and scanned books must keep the Original PDF fallback and clear user guidance.

This is **not** an unconditional PASS. It is a release candidate that is defensible for controlled/internal distribution, but not yet fully evidenced for a broad production launch without native acceptance and real-book quality remediation.
